# Refresh policy

The collector keeps all configured characters and their existing dashboard features. Core raid tables run first, one character at a time, and checkpoint the complete roster after each character. Each WCL raid request contains at most two difficulty selections for one metric. A failure in a later metric preserves the metrics already completed.

Actions reads `characters.config.json` on every run. Its actual cron is UTC 04:00, 10:00, 16:00, 22:00 (KST 13:00, 19:00, 01:00, 07:00). The UTC 04:00 run also refreshes meta. Scheduled execution requires `ENABLE_SCHEDULED_REFRESH=true`; Pages deployment requires the existing `ENABLE_PUBLIC_DEPLOY=true`. GitHub may delay scheduled jobs, so the dashboard labels the next time as scheduled, not a completion guarantee.

Manual modes are `characters` (default), `meta` (no character-table or Raider.IO rescan), `all`, and `cache` (UI rebuild with zero provider API calls and unchanged data timestamps). The legacy `refresh_meta` checkbox also enables meta with character mode. `force_refresh` bypasses application TTLs only; it never bypasses a server cooldown or point-budget admission.

Application cache TTLs are four hours for each raid metric/difficulty, twelve hours for character WCL details, and twenty-four hours for spec meta, successful meta queries, and zone/schema metadata. Failed and null responses are not cached as successful empty results. Valid empty ranking arrays may be cached. A partially completed meta run resumes from successful encounter queries, including empty results, rather than repeating them. Successful sections retain their original timestamps on cache reuse. No synthetic records are published.

Every normal GraphQL request includes `rateLimitData { limitPerHour pointsSpentThisHour pointsResetIn }` in the same operation. Admission uses only a complete, finite numeric response; there is no assumed fixed hourly allowance or IP-wide limit. Twenty percent reserve, observed maximum cost per selection, a twenty-minute run budget, and 1.5-second request spacing are application policies. If quota telemetry is unavailable, low-priority detail/meta requests are deferred and core collection is bounded to one character for that run. An expired sample is unknown, never assumed replenished.

429 immediately stops later provider requests for the run. Retry-After seconds and HTTP dates are honored and persisted to `cache/wcl-runtime.json`; a subsequent run checks that deadline before OAuth. Short transient network/5xx failures retry with exponential backoff; waits longer than thirty seconds defer to the next run. The HTTP queue parses quota telemetry before admitting the next request. No extra quota-only request is used; a normal zone identity query can refresh an unknown budget without rescanning characters.

Actions saves snapshot, runtime cursor/cooldown, and successful query cache even if a later step fails. Before collection it compares the restored snapshot with the already public snapshot and chooses the newer one. Credentials and OAuth responses are never put in these files. Runtime summaries expose actual HTTP attempts, retries, 429s, waits, cache hits, deferred work, and observed quota values, without credentials. The public dashboard distinguishes actual raid success, snapshot execution time, cached data, unavailable data, and deferred refreshes.

Schema/zone and quota behavior must still be validated against actual provider responses when the server permits the next run. Mock tests establish local behavior; they do not establish a provider quota allowance.
