# Refresh policy

The collector keeps all configured characters and their existing dashboard features. Core raid tables run first, one character at a time, and checkpoint the complete roster after each character. Each WCL raid request contains at most two difficulty selections for one metric. A failure in a later metric preserves the metrics already completed.

Actions reads `characters.config.json` on every run. Its actual cron is UTC 04:00, 10:00, 16:00, 22:00 (KST 13:00, 19:00, 01:00, 07:00). Every scheduled run uses `characters`; 04:00 has no additional regional meta collection. Scheduled execution requires `ENABLE_SCHEDULED_REFRESH=true`; Pages deployment requires the existing `ENABLE_PUBLIC_DEPLOY=true`. GitHub may delay scheduled jobs, so the dashboard labels the next time as scheduled, not a completion guarantee.

Manual modes are `characters` (default), `cache` (UI rebuild with zero provider API calls and unchanged data timestamps), and `patches` (official raid patch metadata only). The regional `meta`/`all` choices and `refresh_meta` input are removed. Legacy `REFRESH_SCOPE=meta` or `all` safely aliases `characters`; `REFRESH_META` has no effect. `force_refresh` bypasses application TTLs only; it never bypasses a server cooldown or point-budget admission.

Application cache TTLs are four hours for each raid metric/difficulty and twenty-four hours for zone/schema metadata. Failed and null responses are not cached as successful empty results. Successful sections retain their original timestamps on cache reuse. No synthetic records are published.

After removal of the character detail page, collection no longer requests regional spec leaderboards/trinkets, character WCL dungeon rankings, damage composition, or per-encounter raid dates. Raider.IO profile requests retain score/ranks, best runs and gear; recent runs and talents are neither requested nor stored. Raid performance (including All Stars), official raid patch metadata, dungeon ordering metadata, title cutoff, collection statuses and runtime telemetry remain. Old snapshots with retired fields and new snapshots without them both pass schema validation and published-bundle restore. Normal/cache/patches output drops retired fields, including those in retained records, without changing retained values or timestamps used by the dashboard. The first cache deployment can consume the last public legacy snapshot; a later owner-approved `characters` refresh produces fresh dashboard data. The old parse-date cache is neither read nor saved by Actions.

Every normal GraphQL request includes `rateLimitData { limitPerHour pointsSpentThisHour pointsResetIn }` in the same operation. Admission uses only a complete, finite numeric response; there is no assumed fixed hourly allowance or IP-wide limit. Twenty percent reserve, observed maximum cost per selection, a twenty-minute run budget, and 1.5-second request spacing are application policies. If quota telemetry is unavailable, core collection is bounded to one character for that run. An expired sample is unknown, never assumed replenished. Legacy runtime stage cost records remain readable; retired detail/meta WCL stages are no longer run.

429 immediately stops later provider requests for the run. Retry-After seconds and HTTP dates are honored and persisted to `cache/wcl-runtime.json`; a subsequent run checks that deadline before OAuth. Short transient network/5xx failures retry with exponential backoff; waits longer than thirty seconds defer to the next run. The HTTP queue parses quota telemetry before admitting the next request. No extra quota-only request is used; a normal zone identity query can refresh an unknown budget without rescanning characters.

Actions saves snapshot, runtime cursor/cooldown, and successful query cache even if a later step fails. Before collection it compares the restored snapshot with the already public snapshot and chooses the newer one. Credentials and OAuth responses are never put in these files. Runtime summaries expose actual HTTP attempts, retries, 429s, waits, cache hits, deferred work, and observed quota values, without credentials. The public dashboard distinguishes actual raid success, snapshot execution time, cached data, unavailable data, and deferred refreshes.

Schema/zone and quota behavior must still be validated against actual provider responses when the server permits the next run. Mock tests establish local behavior; they do not establish a provider quota allowance.

A normal credentialed run promotes a previous `raiderio-only` snapshot to `full` after WCL bootstrap succeeds. Cache builds preserve the previous mode. If OAuth or bootstrap fails, the previous mode remains: existing full WCL data is retained with its original timestamps and deferred status, while public-only snapshots keep their public-only warning and do not claim WCL success. A first credentialed run without a previous mode uses `full`, with unavailable/deferred collection states when WCL fails.
